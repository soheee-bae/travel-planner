# 06. 기능과 알고리즘

## 6.1 뷰 구성

스크린샷의 3개를 유지하고 4개를 추가한다.

| 뷰 | 단계 | 역할 |
| --- | --- | --- |
| **일정** (타임라인) | 1 | 스크린샷 그대로. 시간·카테고리·금액·도보시간 |
| **후보 풀** | 1 | 미배치 장소 보관함. 여기서 DAY로 보내는 것이 주 작업 흐름 |
| **지도** | 2 | 번호 마커 + 경로선. 일차별 색상. 미배치는 회색 핀 |
| **비용** | 2 | 총액, 카테고리 비율, 일자별 내역, 예상 vs 실제 |
| **클러스터 제안** | 3 | 위치로 묶은 그룹을 카드로 제시. 수락하면 그 날에 일괄 배정 |
| **오늘** (Today) | 3 | 여행 중 전용. 다음 일정, 남은 시간, 근처 후보, 지도 앱 딥링크 |
| **예약** | 4 | 항공·숙소·신칸센 확정 정보와 예약번호 |

**후보 풀을 별도 뷰로 올린 것이 가장 중요한 변경이다.** "관광지·맛집·카페를 먼저
리스트업하고 당일에 근처 것 중에서 고른다"는 실제 사용 방식에서, 미배치 목록이
일급 화면이 아니면 앱을 쓰는 순서가 어색해진다.

`오늘` 뷰는 여행 기간 중일 때만 탭에 나타난다. 평소에는 존재를 숨긴다.

## 6.2 후보 풀 워크플로우

```
장소 추가 (검색 or 직접 입력)
   └─ places 에 저장, 미배치 상태
        ├─ 카테고리·우선순위·예상비용·예상소요시간·영업시간 입력
        └─ 좌표는 지오코딩으로 자동 (실패 시 지도에서 핀 찍기)

배치
   ├─ (A) 후보 풀에서 멀티셀렉트 → 시트에서 "DAY 2로 이동"
   ├─ (B) 드래그해서 DAY 타임라인에 드롭
   └─ (C) 클러스터 제안 수락 → 그룹 전체가 한 번에 배정

배치 해제
   └─ 항목을 후보 풀로 되돌리기 (삭제가 아니다)
```

**삭제와 배치 해제를 명확히 구분한다.** 일정에서 카드를 스와이프하면 기본 동작은
"후보로 되돌리기"이고, 삭제는 한 단계 더 들어가야 한다. 여행 준비 중 애써 모은
장소를 실수로 지우는 일이 실제로 자주 생긴다.

우선순위 3단계(`필수 / 가고싶음 / 여유되면`)를 두는 이유는 클러스터 제안과
경고 검사의 입력값으로 쓰기 위해서다. "필수인데 아직 미배치"는 경고 대상이다.

## 6.3 DnD와 멀티셀렉트

| 항목 | 규칙 |
| --- | --- |
| 드래그 시작 | 롱프레스 200ms + 이동 허용치 8px. 스크롤과 충돌 방지 |
| 드롭 대상 | 같은 DAY 내 재정렬 / 다른 DAY로 이동 / 후보 풀로 되돌리기 |
| 순서 계산 | 드롭 위치의 앞뒤 항목 id만 서버로 보내고, `reorder_item` RPC가 중간값 계산 |
| 자동 스크롤 | 화면 상·하단 64px 존에서 가속 스크롤 |
| 선택 모드 진입 | 카드 롱프레스 또는 헤더의 "선택" 버튼 |
| 선택 중 액션 | DAY N으로 이동 / 시간 자동배치 / 후보로 되돌리기 / 삭제 |
| 선택 개수 알림 | `aria-live="polite"`로 "3개 선택됨" |
| 키보드 | dnd-kit 키보드 센서. Space로 집고 화살표로 이동, Enter로 놓기 |

모바일에서는 **멀티셀렉트가 주 경로**다. 긴 리스트를 손가락으로 끌어 옮기는 것은
정확도가 낮고, 화면 밖으로 나가면 자동 스크롤에 의존해야 한다. 드래그는 인접한
두세 칸을 바꿀 때만 실제로 편하다. 두 경로를 다 제공하되 UI 상 우선순위는
멀티셀렉트에 둔다.

## 6.4 위치 기반 일정 구성

두 단계로 분리한다. 섞으면 둘 다 나빠진다.

### 1단계 — 같은 날에 갈 것 묶기 (클러스터링)

```sql
-- suggest_day_clusters(p_trip_id, p_k) 내부
select id, name,
       st_clusterkmeans(geom_local, p_k) over () as cluster_id
from (
  select id, name,
         -- 경도를 cos(중심위도)로 축소해 등거리 근사 좌표계로 변환
         st_makepoint(lng * cos(radians(:center_lat)), lat) as geom_local
  from places
  where trip_id = p_trip_id and geog is not null
) s;
```

**좌표를 그대로 k-means에 넣으면 안 된다.** 위경도는 도(degree) 단위라서 1°의
실제 거리가 경도·위도에서 다르다. 나고야(위도 약 35°N)에서 경도 1°는 위도 1°의
약 0.82배다. 보정 없이 클러스터링하면 동서 방향으로 부당하게 뭉친다.
경도에 `cos(중심위도)`를 곱하는 것만으로 도시 규모에서는 충분히 정확하다.
더 엄격하게 하려면 여행 중심점의 UTM 존으로 `ST_Transform`한다.

| 상황 | 알고리즘 |
| --- | --- |
| 후보가 도시 전역에 고르게 퍼짐 | `ST_ClusterKMeans(k = 여행일수)` |
| 밀도가 불균일 (번화가 집중 + 외곽 몇 개) | `ST_ClusterDBSCAN(eps, minpoints)` — 외곽은 노이즈로 남고 별도 처리 |

k-means는 **모든 점을 반드시 k개 그룹에 넣는다**는 특성이 있어서, 지브리 파크처럼
멀리 떨어진 한 곳이 억지로 어느 그룹에 붙는다. DBSCAN은 그런 점을 노이즈로
분리해주므로 "이건 단독 날에" 판단을 만들기 쉽다. 실제로는 DBSCAN으로 먼저
외곽을 걷어내고, 남은 것에 k-means를 돌리는 2패스가 결과가 가장 자연스럽다.

추가 가중치:

- **숙소 위치** — 숙소에서 먼 클러스터는 이동시간이 앞뒤로 2번 붙는다
- **`est_duration_min` 합** — 하루 총 체류시간이 8시간을 넘으면 클러스터를 쪼갠다
- **`priority`** — 필수 장소는 반드시 어느 날에든 들어가야 한다
- **영업 요일** — 월요일 휴관인 미술관은 월요일 클러스터에 넣을 수 없다

### 2단계 — 하루 안의 순서 (경로 최적화)

이동시간 행렬을 만들고 최소 경로를 찾는다. 규모가 작아서 정확하게 풀 수 있다.

| 장소 수 | 방법 |
| --- | --- |
| n ≤ 12 | **Held-Karp 정확해.** 연산량 `2^n · n²` ≈ 59만 → 브라우저에서 수십 ms |
| n > 12 | Nearest Neighbor 초기해 + 2-opt 개선 (수렴까지 반복) |

실제 문제는 순수 TSP가 아니라 **시간창이 있는 TSP(TSPTW)**다. 제약을 이렇게 넣는다.

1. `locked = true` 항목(예약된 식당, 지정 시간 입장권)은 위치를 고정한다.
2. 관광지만으로 먼저 순서를 정한다.
3. 누적 시간이 식사 시간대(11:30–14:00 / 18:00–20:30)에 진입하는 지점을 찾고,
   **그 시점의 위치에서 가장 가까운 식당 후보**를 삽입한다. 이게 "근처에 있는 것 중에
   내가 리스트업한 것에서 고른다"는 방식과 정확히 일치한다.
4. 카페는 관광지 사이 간격이 가장 큰 지점(휴식이 필요한 곳)에 삽입한다.
5. 시작·종료를 숙소로 고정한다.
6. 각 후보의 영업시간을 검사해 위반이 있으면 순서를 한 칸씩 밀어 재검사한다.

### 제안일 뿐, 적용이 아니다

계산 결과는 **미리보기 카드**로 보여주고 사용자가 수락한다. 자동 확정하지 않는다.
"계획적이면서 즉흥적"이라는 사용 방식에서 자동 배치를 강제하면 즉흥성이 사라지고,
알고리즘이 놓친 맥락(그 날 컨디션, 날씨, 현장 대기줄)을 반영할 여지가 없어진다.

제안 카드는 이렇게 제시한다.

```
┌──────────────────────────────────────┐
│ 사카에 · 나고야역 주변 5곳            │
│ 총 이동 42분 · 체류 6시간 20분        │
│ 코메다 커피 → 오아시스21 → 히츠마부시  │
│ → 마루에이 → 야바톤                   │
│              [ 2일차에 적용 ]  [ 무시 ] │
└──────────────────────────────────────┘
```

## 6.5 이동시간·거리 자동 계산

### 단계적 도입

| 단계 | 방식 | 정확도 | 비용 |
| --- | --- | --- | --- |
| 1 | 하버사인 직선거리 × 우회계수 1.3, 도보 4.5km/h | 대략치 | 무료, 외부 호출 없음 |
| 2 | OSRM (자체 호스팅 또는 공개 인스턴스) — 도보·자차·자전거 | 실제 경로 | 무료 (호스팅 비용) |
| 3 | 상용 Directions API — 대중교통 포함 | 높음 | 유량 과금 |

1단계로 시작해도 UI는 완성된다. `transit_legs.source`가 `'estimate'`이므로
pill에 `~5m`처럼 물결을 붙여 추정임을 명시한다([04](04-design-system.md) §4.6).

```
duration_min = haversine(a, b) × 1.3 / 4.5km/h × 60
```

우회계수 1.3과 보행속도 4.5km/h는 **경험적 heuristic이다.** 격자형 도시에서
직선거리 대비 실제 보행거리 비율로 흔히 쓰이는 값이지만, 이 프로젝트에서 검증한
수치는 아니다. 2단계에서 OSRM 실측값과 비교해 보정한다.

### 대중교통의 현실

- OSRM은 대중교통을 지원하지 않는다. 도로·보행 네트워크 전용이다.
- 대중교통 경로는 상용 API(Google Routes, NAVITIME 등)나 GTFS 기반
  OpenTripPlanner 자체 호스팅이 필요하다. 후자는 운영 부담이 크다.
- **요금 정책은 자주 바뀌므로, 붙이기 전에 현재 단가를 직접 확인해야 한다.
  이 문서에 단가를 적지 않는 이유다.**

### 요금 자동화는 하지 않는다

일본 역간 운임은 공개 API로 안정적으로 얻기 어렵다. 스크린샷의 `¥1,170`
(센트레아→뮤스카이) 같은 값은 **수동 입력 + 자주 쓰는 구간 프리셋**으로 처리하는
것이 현실적이다.

```
구간 프리셋 (사용자별 저장)
  센트레아 ↔ 나고야 (뮤스카이)   ¥1,170
  지하철 1구간                    ¥210
  지하철 2구간                    ¥240
  1일 승차권                      ¥760
```

한 번 입력한 구간은 이후 자동 완성된다. 완전 자동화보다 이쪽이 정확하고 빠르다.

### 캐시 전략

```
경로 요청
  └─ 좌표를 소수 5자리로 반올림 (≈1.1m)
       └─ route_cache 조회
            ├─ 히트 → 즉시 반환 (외부 호출 0)
            └─ 미스 → 외부 API 호출 → route_cache 기록 → 반환
```

도보·자차 경로는 사실상 변하지 않으므로 **TTL을 두지 않는다.** 여행이 여러 개여도
캐시를 공유하므로 재방문 도시에서는 호출이 거의 발생하지 않는다.

N개 장소의 순서 최적화에는 N×N 행렬이 필요하다. 개별 호출로 하면 n=10에서 90번이다.
**Matrix/Table 엔드포인트로 한 번에 받는다** (OSRM `/table`, 상용 API의 matrix).

## 6.6 비용 자동 계산

### 자동 생성

| 계기 | 동작 |
| --- | --- |
| 장소를 DAY에 배치 | `places.est_cost`가 있으면 `expenses` 행을 예상 비용으로 자동 생성 |
| 이동 구간 계산 | `transit_legs.fare`가 있으면 `transport` 카테고리로 자동 반영 |
| 예약 등록 | `bookings.amount`를 해당 날짜의 `stay`/`transport` 비용으로 |
| 사용자 수정 | 자동 생성 행에 `is_manual` 플래그를 세워, 이후 자동 갱신이 덮어쓰지 않게 함 |

**자동 생성한 값을 사용자가 고친 뒤 다시 자동으로 덮어쓰는 것**이 이런 기능에서
가장 흔한 버그다. 플래그 하나로 막는다.

### 집계

프론트에서 계산하지 않는다. `trip_cost_by_day`, `trip_cost_by_category`,
`trip_totals` View가 담당한다([02](02-data-model.md) §2.6). 항목 하나를 수정하면
Realtime → 쿼리 무효화 → View 재조회 순으로 파이차트와 일자별 내역이 자동으로 맞는다.

### 환율

- 여행 생성 시 `trips.fx_rate`에 스냅샷을 저장한다. 나중에 환율이 변해도 과거
  계획의 원화 환산액이 흔들리지 않는다.
- 여행 중에는 하루 1회 최신 환율을 받아 "오늘 환율 기준" 값을 병기한다.
- 표시: `¥29,880 (≈ ₩286,000)`. 원화는 백 원 단위로 반올림한다 — 환율 자체가
  근사치인데 원 단위까지 보여주면 정확해 보이는 착시가 생긴다.

### 예상 vs 실제

여행 전에는 예상만, 여행 중에는 실제를 입력한다. 비용 뷰에서 두 값을 나란히 보여주고
차이를 강조한다. 예산(`trips.budget`)이 있으면 잔액 게이지를 상단에 둔다.

인원수(`trips.headcount`)로 나눈 1인당 금액도 함께 표시한다.

## 6.7 경고 검사

자동으로 고치지 않는다. **알려주고 사용자가 결정한다.** 일정 카드에 노란 배지로 표시.

| 경고 | 판정 |
| --- | --- |
| 영업시간 위반 | `start_time`~`end_time`이 `opening_hours`의 영업 구간 밖 |
| 휴무일 | 해당 요일이 정기 휴무 |
| 시간 겹침 | 같은 DAY의 두 항목 시간 구간이 교차 |
| 이동시간 부족 | 앞 항목 종료 ~ 뒤 항목 시작 간격 < `transit_legs.duration_min` |
| 과밀 일정 | 하루 총 (체류 + 이동) > 12시간 |
| 미배치 필수 장소 | `priority = 2`인데 `day_id IS NULL` |
| 마지막 날 이동 위험 | 공항 출발 전 여유 < 90분 |

**이동시간 부족 경고가 실사용에서 가장 유용하다.** 시간을 손으로 채우면 이동시간을
빼먹기 쉽고, 현장에서 그게 한 번 밀리면 그 날 뒤쪽 전체가 무너진다.

두 기능이 핵심이다.

- **지연 반영** — "15분 늦어짐"을 누르면 `locked`가 아닌 이후 항목의 시간을 일괄로
  밀고, 영업시간 위반이 생기면 경고한다.
- **근처 후보** — 현재 위치(GPS)에서 `nearby_places` RPC로 반경 내 미배치 후보를
  거리순으로 보여준다. "계획에 없었지만 근처니까 들르는" 즉흥성을 지원한다.

## 6.9 추가 아이디어

우선순위 순.

| 아이디어 | 내용 | 가치 |
| --- | --- | --- |
| **지도 링크 붙여넣기** | 구글맵/네이버 지도 공유 URL을 붙이면 이름·좌표를 파싱해 후보로 추가 | 장소 등록이 가장 귀찮은 작업이다. 이걸 줄이는 게 체감 1위 |
| **장소 라이브러리** | 여행 간 장소 재사용. 이전 나고야 여행의 후보를 새 여행으로 복사 | 재방문 도시에서 반복 입력 제거 |
| **날씨 연동** | 일자별 예보를 받아 우천 시 실외 관광지에 경고 + 실내 후보 대안 제시 | 일정을 실제로 바꾸게 만드는 정보 |
| **읽기 전용 공유** | 동행자에게 링크 전달. 로그인 불필요 | 함께 가는 사람이 항상 있다 |
| **오프라인 내보내기** | 일정을 이미지/PDF로 저장 | 해외 데이터가 끊길 때의 최후 수단 |
| **영수증 입력** | 카메라로 금액만 빠르게 입력 (OCR은 과함, 숫자 키패드 우선) | 여행 중 실제 지출 기록의 마찰 감소 |
| **대기시간 메모** | 방문 후 "대기 30분" 기록 → 다음 여행의 예상 소요시간에 반영 | 재방문 시 정확도 향상 |
| **회고 모드** | 여행 후 사진 + 실제 지출 + 별점. 다음 계획의 입력값 | 데이터가 쌓이면 개인화 가능 |
| **동행자 공동 편집** | `trip_members` + Realtime으로 이미 구조는 준비됨 | 필요 여부는 사용 패턴에 따라 |

`지도 링크 붙여넣기`를 1순위로 둔 이유: 이 앱의 실제 병목은 계획을 짜는 것이 아니라
**장소를 입력하는 것**이다. 관광지·맛집·카페를 수십 개 리스트업하는데 매번 이름 검색,
좌표 확인, 카테고리 선택을 하면 앱을 쓰는 것 자체가 일이 된다.
URL 하나 붙이면 끝나야 한다.
