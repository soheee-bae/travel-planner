# 09. 결정 필요 항목

계획서 v2를 `docs/01`~`07`(v1 설계)과 대조해 나온 충돌·미결 사항이다.
`D1`, `D2`, `D10`은 **Phase 1을 시작하기 전에** 정해야 한다. 나머지는 해당 Phase
진입 전까지 정하면 된다.

## 확정 사항 (2026-09-03)

| # | 결정 | 확정값 |
| --- | --- | --- |
| D1 | 스타일링 | **Tailwind CSS v4 + shadcn/ui.** Emotion은 이 프로젝트에서 미사용 |
| D2 | 데이터 레이어 | **React Query + MSW.** zustand는 서버 상태가 아닌 UI 상태(선택 모드, 시트 열림, 지도 카메라)에만 사용 |
| D10 | 디자인 방향 | **Notion 느낌(웜 미니멀리즘·serif 헤딩·soft surface)으로 진행.** 카테고리 칩 팔레트는 스크린샷 실측값을 유지 (§D10-A 참조) |

아래 D1·D2·D10 섹션의 "선택지/권장" 서술은 **결정 배경 기록**으로 남겨두고,
이후 서술은 확정값을 전제로 한다.

각 항목은 사실관계 → 선택지 → 권장안 순으로 적었다. 권장안은 의견이고, 근거는
사실이다.

## D1. Tailwind + shadcn/ui vs Emotion 〔차단〕

### 사실

계획서 v2는 **Tailwind CSS + shadcn/ui + getdesign.md Notion 디자인 시스템**을
지정한다. 반면 사용자의 전역 개발 룰은 **"Styling: Use Emotion (CSS-in-JS)"**
이다. 둘은 양립하지 않는다.

- shadcn/ui는 Tailwind 클래스로 스타일을 작성한 컴포넌트 소스를 프로젝트에 복사하는
  방식이다. Emotion으로 쓰려면 모든 컴포넌트를 다시 작성해야 하므로 도입 이점이 사라진다.
- getdesign.md의 Notion 디자인 시스템도 Tailwind 토큰 전제다.
- 반대로 Emotion에는 App Router 제약이 있다. Server Component에서 동작하지 않아
  화면 대부분이 Client Component가 된다([01](01-architecture.md) §1.2).

### 선택지

| 안 | 내용 | 대가 |
| --- | --- | --- |
| **A** | Tailwind + shadcn/ui 채택, 이 프로젝트에서 Emotion 룰 예외 | 전역 룰과 불일치 |
| B | Emotion 유지, shadcn/ui 포기 | UI 프리미티브 전부 직접 구현. Notion 디자인 시스템 활용 불가 |
| C | Tailwind로 레이아웃, Emotion으로 동적 스타일 | 두 시스템 병존. 어디에 무엇을 쓸지 매번 판단해야 함. 비추천 |

### 권장: **A**

계획서 v2가 최신 의사결정이고, shadcn/ui + Notion 시스템이 이 프로젝트의 디자인
방향 자체를 정의한다. Emotion을 지키려면 그 둘을 다 버려야 하는데 그건 계획서를
버리는 것과 같다. 전역 룰은 "기본값"이고 프로젝트별 예외는 정상이다.

단 A를 택하면 결정해야 할 게 하나 더 있다. **Tailwind v4는 설정 파일 없이 CSS의
`@theme`으로 토큰을 정의하는 방식으로 바뀌었다.** v3 방식 문서를 보고 작업하면
맞지 않으므로, 시작 시점에 v4 기준으로 잡는다.

## D2. zustand + mock vs React Query + MSW 〔차단〕

### 사실

계획서 v2는 "API 키 없이 시작. 로컬 상태(zustand) + mock 데이터로 작동하게 만들고
Supabase는 Phase 10에서 연동"이라고 정했다. 한편 사용자 전역 룰은 **"React Query에
전적으로 의존. 서버 상태를 로컬 useState에 복제하지 말 것"**이다.

여기서 중요한 건 룰 위반 여부보다 **Phase 10의 재작업 규모**다.

- zustand 스토어에 데이터를 담으면, 컴포넌트가 `useTripStore()`를 호출한다.
  Phase 10에서 Supabase를 붙이면 그 호출부 전부가 비동기 상태(로딩·에러·재검증)를
  다루도록 바뀌어야 한다. Phase 2~9에서 만든 모든 화면이 영향받는다.
- React Query + MSW로 시작하면 컴포넌트는 처음부터 `useQuery`/`useMutation`을 쓴다.
  Phase 10은 **MSW 핸들러를 실제 Supabase 호출로 교체하는 작업**이고, 컴포넌트는
  건드리지 않는다.

두 방식 모두 "API 키 없이 UI부터 만든다"는 계획서 의도를 만족한다. 차이는 나중에
치를 비용뿐이다.

### 권장: **React Query + MSW**

계획서의 Phase 순서(UI 우선)는 그대로 유지하고, mock 계층만 zustand에서 MSW로
바꾸는 것이다. 계획을 뒤집는 게 아니라 같은 계획을 더 싸게 실행하는 방법이다.

zustand는 서버 상태가 아닌 것에만 쓴다 — 선택 모드, 시트 열림, 지도 카메라 상태 등.

## D10. 디자인 방향 충돌 — 스크린샷 vs Notion 스타일 〔차단〕

### 사실

두 디자인 소스가 서로 다른 방향을 가리킨다.

| | 업로드한 스크린샷 (실측값) | getdesign.md Notion 스타일 |
| --- | --- | --- |
| 배경 | 쿨 그레이·블루 `#EEF2F9` | 웜 미니멀리즘 (베이지·오프화이트 계열) |
| 강조 | 파랑 `#3762E3` | 뉴트럴 중심, 낮은 채도 |
| 제목 | 산세리프 굵게 | **serif headings** |
| 표면 | 흰 카드 + 1px 보더, 그림자 없음 | soft surfaces |
| 중립색 | Tailwind gray 스케일과 거의 일치 | 별도 웜 그레이 |

스크린샷의 색은 내가 픽셀에서 직접 추출한 값이라 정확하다([04](04-design-system.md) §4.2).
Notion 스타일을 그대로 적용하면 스크린샷과 눈에 띄게 다른 앱이 된다.

### 선택지

| 안 | 내용 |
| --- | --- |
| A | Notion 스타일 전면 채택. 스크린샷은 **레이아웃·정보구조 참고용**으로만 사용 |
| B | 스크린샷 실측 토큰 유지. Notion에서는 여백·타이포 리듬만 차용 |
| C | 하이브리드 — 웜 뉴트럴 배경 + 스크린샷의 카테고리 팔레트 |

### 권장: **A 또는 C**, 단 명시적으로 고를 것

계획서가 Notion 시스템을 스택 표에 넣었으니 A가 계획서에 충실하다. 다만 스크린샷을
"참고 디자인"으로 올린 의도가 색감까지 포함이라면 B/C가 맞다.

**어느 쪽이든 카테고리 팔레트는 스크린샷 값을 쓰는 걸 권한다.** 관광/교통/식사/이동/쇼핑
칩 색을 실측해뒀고 명도 대비 검증까지 끝났다. 이 부분만 재사용하면 접근성 작업을
다시 하지 않아도 된다.

접근성 관련해서 이미 확인된 사실 하나: 스크린샷의 금액 초록 `#43946C`(흰 배경 3.69:1)과
빨간 배지 `#DD524C`(흰 글자 3.9:1)는 **WCAG AA 4.5:1에 미달**한다. 어떤 디자인
방향을 택하든 이 두 색은 조정이 필요하다(제안값 `#2E7D57`, `#C63F39`).

### D10-A. 확정 — Notion 느낌으로 채택. 실제 Notion 토큰 조사 결과

여러 Notion 디자인 시스템 분석(DesignMD, Duply, webdesignhot 등)을 대조해 공통으로
나오는 값을 뽑았다. 마케팅 사이트와 실제 앱은 다르므로, **앱 내부 UI에 맞는 값만
채용**하고 마케팅 전용 요소(네이비 히어로 배너, 보라 CTA)는 가져오지 않는다.

| 토큰 | Notion 실측값 | 이 프로젝트 적용 |
| --- | --- | --- |
| 캔버스 | `#FFFFFF` | 그대로 사용 |
| 웜 서페이스 | `#F6F5F4` | 페이지 배경으로 사용 (v1의 쿨톤 `#EEF2F9` 대체) |
| 보더 | `#DFDCD9` | 카드 보더 (v1의 `#E6E7EB` 대체) |
| 텍스트(본문) | `rgba(0,0,0,0.9)` ≈ `#191919` | 그대로 사용 |
| 텍스트(보조) | `#615D59` / `rgba(0,0,0,0.54)` | 그대로 사용, 대비 재검증 필요 |
| 액션 블루 | `#0075DE` | 강조색으로 사용 (v1의 `#3762E3` 대체) |
| 라운딩 | 8~12px | v1과 거의 동일하게 유지 |
| 타이포 | NotionInter(대체: Inter/Pretendard) 본문 + **Lyon Text(세리프, 헤딩 전용)** | 본문은 Pretendard 유지, 페이지 타이틀 등 대형 헤딩에만 세리프 적용 |

**세리프는 "가끔"이 핵심이다.** Notion 시스템도 세리프를 큰 섹션 타이틀에만 쓰고
본문·UI 텍스트는 전부 산세리프다. Lyon Text는 상용 폰트라 대체가 필요하고, 한글을
지원해야 하므로 **Noto Serif KR**(Google Fonts, 한글+라틴 지원)을 채택한다.
적용 범위는 페이지 타이틀(`여행 플래너`, 여행 이름 헤더)과 각 탭의 섹션 헤딩 정도로
좁게 잡는다. 카드 제목·본문·버튼·탭 라벨은 계속 Pretendard다.

**카테고리 칩 팔레트는 그대로 재사용한다.** 관광/교통/식사/이동/쇼핑/카페/숙소
칩의 배경·텍스트·차트 fill 값은 v1에서 이미 명도 대비 검증을 마쳤고(§04 §4.2),
웜 배경으로 바뀌어도 칩 자체는 흰/파스텔 배경 위에 얹히므로 대비가 흔들리지 않는다.

**대비 재검증 결과** (배경이 `#EEF2F9`→`#F6F5F4`, 강조색이 `#3762E3`→`#0075DE`로
바뀌면서 다시 계산):

| 조합 | 대비 | 판정 |
| --- | --- | --- |
| `#191919` on `#FFFFFF` | 17.58:1 | AAA |
| `#615D59` on `#FFFFFF` | 6.53:1 | AA |
| `#615D59` on `#F6F5F4` | 5.99:1 | AA |
| `#FFFFFF` on `#0075DE` (버튼 라벨) | 4.57:1 | AA (경계값, 굵게 권장) |
| `#0075DE` on `#FFFFFF` (링크·활성 탭) | 4.57:1 | AA (경계값) |

(위 4개 수치는 실제로 계산기를 돌려 검증한 값이다. 처음 초안에서 5.4/5.1/17.9/4.6로
적었던 것은 어림값 오류였다.)

`#0075DE`가 경계값이라 **버튼·활성 탭 텍스트는 15px 이상 + 500 굵기 이상**으로
제한한다. 더 안전하게 가려면 `#0068C7`(대비 5.52:1)로 살짝 눌러도 되지만, Notion
고유의 액션 블루 느낌을 유지하기 위해 원본값을 우선 채택하고 실기기 QA에서
가독성을 재확인한다.

## D3. Next.js 15 vs 16

### 사실

계획서는 Next.js 15를 지정했다. npm 최신 stable은 **16.3.4**(2026-09 확인)이다.
Next 16의 관련 변경점:

- `middleware.ts` → **`proxy.ts`** 로 이름 변경, Node.js 런타임 전용. 구 파일은
  deprecated. Supabase 세션 갱신 코드가 여기 들어간다.
- View Transitions가 App Router에서 **무설정으로 동작**한다
  (`import { ViewTransition } from 'react'`, `<Link transitionTypes={[...]}>`).
  P2-06의 카드→디테일 전환을 Framer Motion 없이 처리할 수 있다.
- Turbopack, Cache Components 안정화.

### 권장: **16**

새 프로젝트를 한 메이저 뒤에서 시작할 이유가 없다. 특히 `proxy.ts` 전환은 Phase 10에서
어차피 마주치므로 처음부터 16으로 잡는 게 싸다.

다만 **Framer Motion으로 페이지 전환 exit 애니메이션은 App Router에서 제대로 안 된다.**
라우터가 이전 페이지를 즉시 언마운트해서 붙잡을 훅이 없다. 그래서 역할을 이렇게 나누길
권한다.

- **페이지 전환** (랜딩 ↔ 디테일): View Transitions
- **제스처·스프링** (시트 드래그, 탭 스와이프, 누름 피드백): Framer Motion

## D4. 지도 이중 제공자 범위

### 사실

계획서는 Naver(한국) + Google(해외) 두 제공자를 국가코드로 분기한다.
플래너 탭은 이 프로젝트에서 가장 복잡한 화면이고, 제공자를 2개 만들면 마커·폴리라인·
카메라 제어·이벤트 처리를 두 번 구현·두 번 테스트해야 한다.

확인이 필요한 사항이 몇 가지 있다. **아래 수치와 요건은 내가 검증하지 않았다.**

- 계획서의 "Naver 월 600만 무료" — 현재 정책을 직접 확인해야 한다.
- Naver Maps는 네이버 클라우드 플랫폼 계정과 서비스 도메인 등록이 필요하다.
- Naver Maps는 국내 전용이다. 업로드한 스크린샷은 **나고야**(일본) 일정이므로
  이 데이터로는 Naver 경로가 아예 테스트되지 않는다.
- Google Maps Platform 요금 체계는 최근 몇 년간 여러 번 바뀌었다. 단가는 직접 확인.

### 권장: **어댑터 인터페이스 먼저, 구현은 1개부터**

`P6-01`에서 `MapProvider` 인터페이스를 먼저 정의하고, `P6-02`로 **한 제공자만**
구현해서 플래너 탭을 완성한다. 두 번째 제공자(`P6-03`)는 실제로 그 나라 여행을
만들 때 추가한다.

어느 쪽을 먼저 만들지는 첫 실사용 여행이 국내인지 해외인지로 결정한다. 스크린샷이
나고야이니 Google이 먼저일 가능성이 높다.

핵심은 **어댑터 경계를 처음부터 두는 것**이다. 이게 없으면 두 번째 제공자를 붙일 때
플래너 탭을 다시 만든다.

## D5. 플래너 탭 — 지도+일정 통합 방식 (계획서 리뷰 요청 항목)

계획서가 A(전체화면 지도 + 바텀시트) / B(탭 분리) / C(토글) 중 확인을 요청했다.

### 권장: **A**

근거 셋.

1. **B는 A의 부분집합이다.** 바텀시트를 full 스냅까지 올리면 사실상 일정 전용 화면이
   되고, 내려면 지도 전용이 된다. A는 사용자가 비율을 직접 조절하는 방식이라 B가
   할 수 있는 걸 다 할 수 있다.
2. **업로드한 지도 스크린샷이 이미 이 문제를 보여준다.** 지도가 화면의 절반쯤을
   차지하고 아래 `방문 순서` 리스트는 5번 항목에서 잘려 있다. 둘 다 좁다.
3. **"가까운 것끼리 같은 날에" 배치하려면 지도와 리스트를 동시에 봐야 한다.**
   탭을 왕복하면 위치 감각이 끊긴다.

### 다만 A에는 조건이 붙는다

**제스처 충돌이 이 프로젝트 최대 난이도다.** 같은 화면에서 세 가지 드래그가 경쟁한다.

| 동작 | 충돌 상대 |
| --- | --- |
| 지도 팬 (아래로 끌기) | 바텀시트 내리기 |
| 시트 올리기 (위로 끌기) | 시트 내부 리스트 스크롤 |
| 카드 집기 (롱프레스 후 이동) | 시트 드래그, 리스트 스크롤 |

그래서 `P6-00`을 **버리는 프로토타입으로 먼저** 만들자고 제안했다. 중재 규칙의
출발점은 이 정도다.

- 시트 드래그는 **핸들 영역에서만** 수신한다. 시트 본문에서는 스크롤만.
- 시트가 `full`이고 내부 스크롤이 최상단일 때만 아래 드래그를 시트 내리기로 해석한다.
- 카드 DnD는 롱프레스 200ms + 이동 허용치 8px 이후에만 시작한다.
- iOS 스와이프 뒤로가기 때문에 **화면 왼쪽 24px에서는 수평 드래그를 받지 않는다.**

## D6. 6탭이 448px에 들어가는가

### 사실

계산해보면 라벨을 줄이면 들어간다.

```
max-w-md 448px − 좌우 패딩 16px×2 = 416px
416px ÷ 6탭 = 탭당 69.3px
```

13px 한글 라벨 기준 대략치:

| 라벨 | 글자폭 | 최소 패딩 | 합계 | 69px 내 |
| --- | --- | --- | --- | --- |
| 위시리스트 (5자) | ~65px | 16px | ~81px | ✗ |
| 플래너 (3자) | ~39px | 16px | ~55px | ✓ |
| 리스트 (3자) | ~39px | 16px | ~55px | ✓ |
| 개요·비용·준비·메모 (2자) | ~26px | 16px | ~42px | ✓ |

계획서 본문의 ASCII 다이어그램은 이미 `개요/플래너/리스트/비용/준비/메모`로 되어 있고,
섹션 제목만 `위시리스트`다.

### 권장

- **탭 라벨은 `메모`, 섹션 제목은 `위시리스트`** 로 분리한다. 계획서 다이어그램과 일치한다.
- 아이콘을 같이 넣으려면 아이콘 위·라벨 아래 **세로 배치**로 한다. 가로 배치는 69px에
  안 들어간다.
- 안전장치로 **가로 스크롤 가능한 탭바**로 만든다. 라벨이 하나라도 길어지거나 탭이
  추가될 때 레이아웃이 깨지지 않는다.
- 아이콘만 남기는 건 비추천이다. 6개 아이콘의 의미를 학습해야 하고 접근성도 나빠진다.

## D7. 다크모드 범위

### 사실

계획서의 Verification Plan에 "다크모드 지원 확인"이 있는데, 본문 어디에도 다크모드
설계가 없다. 업로드한 스크린샷도 라이트 모드만이다.

다크모드를 지원하려면 **Phase 1의 토큰 설계 방식이 달라진다.** 색을 `bg-white`처럼
직접 쓰면 안 되고 `bg-surface`처럼 의미 기반 토큰 쌍으로 정의해야 한다. 나중에
넣으려면 모든 컴포넌트의 색 지정을 다시 훑어야 한다.

### 권장: **v1 범위에서 제외, 단 토큰은 의미 기반으로 설계**

다크모드 자체는 나중에 하더라도, `P1-03`에서 토큰 이름을 `surface`/`muted`/`border`
같은 의미 기반으로 잡아두면 나중에 값만 추가해서 켤 수 있다. 비용이 거의 안 든다.

지도가 특히 문제다. 다크모드에서 라이트 지도 타일을 띄우면 화면 절반이 밝게 튄다.
제공자별 다크 스타일이 있는지 확인이 필요하고, 이건 D4와 묶여 있다.

## D8. places 단일 테이블 — 순서 컬럼과 재방문

### 사실 1 — `order_index int`의 문제

계획서 스키마는 `PLACES.order_index int`다. 정수 순번으로 드래그 앤 드롭을 구현하면
카드 하나를 옮길 때 **그 뒤 항목 전부의 번호를 다시 써야 한다.** 10개 리스트에서
맨 앞으로 옮기면 10개 UPDATE가 나간다. 모바일에서 체감이 나빠지고, 낙관적 업데이트
롤백도 복잡해진다.

**권장**: `order_index`를 `numeric`(또는 `double precision`)으로 두고 소수 순번
(fractional index)을 쓴다. 앞뒤 값의 중간값을 계산해 **그 행 하나만** UPDATE한다.
정밀도가 고갈되면 해당 Day만 재정규화하는 안전장치를 둔다.

### 사실 2 — 같은 장소 재방문 표현 불가

`places`에 `day_id`와 `order_index`가 직접 붙어 있으므로 **한 장소는 최대 한 번만
일정에 들어간다.** 표현 못 하는 경우가 있다.

- 마음에 든 카페를 이틀 연속 가기
- 숙소를 매일 저녁 경유지로 넣기
- 같은 역을 환승으로 두 번 지나기

v1 설계는 `places`(후보)와 `itinerary_items`(배치)를 분리해서 이걸 해결했다.

**권장**: 지금은 **계획서 구조를 그대로 수용한다.** 단일 테이블이 단순하고, 재방문은
빈도가 낮다. 필요해지면 `place_visits` 테이블을 추가하는 마이그레이션으로 대응한다.
지금 분리하면 모든 화면이 두 단계 조회를 하게 되어 Phase 2~9가 무거워진다.

이 트레이드오프를 **알고 수용하는 것**이 중요하다. 나중에 "왜 같은 카페를 두 번 못
넣지"라는 질문이 나올 때 설계 실수가 아니라 의도된 선택이었음을 알 수 있어야 한다.

## D9. 스플래시를 라우트로 둘 것인가

### 사실

계획서 구조는 `app/page.tsx`를 로딩 스플래시로, `app/trips/page.tsx`를 랜딩으로 둔다.
스플래시를 라우트로 만들면 문제가 생긴다.

- `/`에서 `/trips`로 이동한 뒤 **뒤로가기를 누르면 스플래시로 돌아간다.**
- PWA standalone에서는 앱을 열 때마다 스플래시 라우트를 거치므로 히스토리가 오염된다.
- 스플래시가 라우트 전환을 유발해서 첫 진입 체감이 오히려 느려진다.

### 권장

`/`를 랜딩으로 두고(또는 `/`에서 `/trips`로 리라이트), **스플래시는 랜딩 위에 얹는
오버레이 컴포넌트**로 만든다. 데이터가 준비되면 페이드 아웃한다. 히스토리에 항목이
남지 않고 뒤로가기 문제도 없다.

PWA를 나중에 붙일 거라면 manifest의 스플래시 화면이 이 역할을 대신하므로,
오버레이는 웹 첫 진입용으로만 유지한다.

## D11. Frankfurter API — 확인 완료 + 주의사항

### 사실 (직접 호출로 검증했다)

```
GET https://api.frankfurter.dev/v1/latest?base=JPY&symbols=KRW
→ {"amount":1.0,"base":"JPY","date":"2026-09-02","rates":{"KRW":8.5376}}
```

- API 키 없이 동작한다. JPY·KRW 모두 지원한다. 계획서 선택이 맞다.
- **`api.frankfurter.app`은 301 리다이렉트를 반환한다.** 현재 정식 호스트는
  `api.frankfurter.dev/v1/...`이다. 리다이렉트를 따르지 않는 fetch 설정에서는
  실패하므로 `.dev` 호스트를 직접 쓴다.
- 응답의 `date`가 **오늘이 아니라 전일**이다(2026-09-03 호출에 2026-09-02 응답).
  ECB 기준 환율이라 영업일 하루 1회만 갱신되고 주말·공휴일에는 값이 멈춘다.

### 권장

여행 경비 환산 용도로는 충분하다. 다만 UI에 **"실시간 환율"이라고 쓰지 않는다.**
`환율 기준일: 9/2` 같은 표기를 함께 보여주는 게 정확하다. 카드 결제 실제 청구액과는
차이가 나므로 근사치임을 명시한다.

원화 환산은 **백 원 단위로 반올림**한다. 환율 자체가 근사치인데 원 단위까지 보여주면
정확해 보이는 착시가 생긴다.
